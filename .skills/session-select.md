Investigate the repo and propose exactly 3–5 candidate topics for the next session. Follow every CLAUDE.md rule, especially "Problem files", "Session selection", and "Datasheet study sessions". Research/report only — no user contact, no AskUserQuestion, no picking a winner. Return findings as text; the calling conversation presents them. No scripts — every lookup is `Read`/`Grep`/`Glob` against `.index/`/`.history/`, per `.index/schema.yml` and `.history/schema.yml`.

## Steps

1. **Sibling repo awareness (informational only — skip entirely if `GITHUB_TOKEN` isn't set, or if this repo's own `origin` remote can't be resolved).** No local clone is kept between sessions — this reads each sibling's live default branch fresh, every time, directly from GitHub; nothing here is ever pulled, updated, or left on disk afterward.
   - Resolve the owner from this repo's own remote, never hardcoded: `git remote get-url origin`, parsed for the `<owner>` segment (works for both `git@github.com:<owner>/<repo>.git` and `https://github.com/<owner>/<repo>.git` forms).
   - List candidates: `curl -s -H "Authorization: token $GITHUB_TOKEN" "https://api.github.com/users/<owner>/repos?per_page=100"`, filter to names ending in `-with-llm`, excluding this repo's own name.
   - Qualify each candidate: `curl -s -o /dev/null -w '%{http_code}' -H "Authorization: token $GITHUB_TOKEN" "https://api.github.com/repos/<owner>/<candidate>/contents/.skills/session-select.md"` — `200` means it uses the full select/plan/close/verify/retro architecture and counts as a real sibling; anything else (e.g. a repo deliberately built without it) is skipped, never assumed.
   - For each qualifying sibling, read its actual default branch from `https://api.github.com/repos/<owner>/<candidate>` (the `default_branch` field) — never assume `master` or `main`.
   - Shallow-clone exactly that branch into a throwaway directory, read what's needed, delete it before this step ends: `git clone --depth 1 --branch "<default_branch>" "https://x-access-token:$GITHUB_TOKEN@github.com/<owner>/<candidate>.git" .tmp/sibling-<candidate>`, then `ls .tmp/sibling-<candidate>/.history/*/*.yml | sort | tail -6` and a quick `Read` of just the `date`/`title` fields (or its `summary.txt` equivalent under `.index/sessions/`) — a handful of the most recent entries is enough, not a full read — then `rm -rf .tmp/sibling-<candidate>`.
   - Purpose is situational awareness only: how recently and how intensely the user has been working elsewhere, and on what topics — never used to justify or rule out a hardware candidate's prerequisites (this repo's scope stays self-contained regardless of what's happening in a sibling repo), and never used to infer personal/psychological conclusions (same "observable facts only, no personality/motivation judgments" rule that governs this repo's own `.history/`). Report activity facts (dates, titles, cadence), not assessments of the person.
   - Report this as its own clearly labeled section in step 7, separate from the candidate list, so the calling conversation can mention it in passing if relevant instead of blending it into candidate rationale.

2. **Done set.** `ls .index/sessions/` (each directory's `meta.yml` `title:` field is the exact Concept Title, and its `target:` field the hardware target) — this IS the done set. Cross-check against the source files under `microbit/`, `cyberpi/`, `raspberry/`, `basys3/`. Fall back to reading every `.history/*/*.yml` in full only if `.index/` looks stale/incomplete (e.g. a source file with no matching `.index/sessions/*/meta.yml` entry).

4. **Dependency graph.** `grep -rl "<concept title>" .index/sessions/*/prerequisites.yml` for reverse "required-by" lookups; `Read .index/sessions/<slug>/derived_from.yml`/`unlocks.yml` for a session's own forward relationships — genuine prerequisites already kept separate from softer `uses_concepts.yml`/`related_to.yml`. `ls .index/branches/` + `Read` each for branch structure, `ls .index/open-gaps/*/` + `Read` each for "what's underexplored". `.history/` carries no dependency field by design — if `.index/` looks stale, re-derive from notes/source files directly, never from a `.history/` `Depends on`/`Unlocks` field (none exists). Use `grep -l '"<title>"' .history/*/*.yml` or `grep -r "<term>" .history/*/*.yml` only for session-event citations (a specific bug, a specific wrong prediction) when needed.

5. **Cross-platform position.** Run `.index/schema.yml`'s `target_frequency` query (`grep -h '^target:' .index/sessions/*/meta.yml | sort | uniq -c | sort -rn`) to see, concretely, how sessions are distributed across micro:bit, CyberPi, and Raspberry Pi — cite the actual counts when a candidate would rebalance coverage. For any peripheral concept already done on one target, check whether the same concept on a different target is a viable, interesting candidate (see CLAUDE.md's "Cross-platform comparison") — `grep -rl "<concept>" .index/sessions/*/related_to.yml` shows if that comparison has already been made.

6. **Generate exactly 3–5 candidates.** Per candidate:
   - Confirm not already in the done set.
   - Confirm its full prerequisite chain is already covered — except the stepping-stone exception in "Session selection", named explicitly with the larger target it unlocks.
   - Classify: harder variant/extension, shared-idea-different-target (cross-platform), gap-filling, or stepping-stone.
   - 1-2 sentences on why it's interesting given what's done.
   - Its prerequisite chain (existing sessions/files it draws on).
   - If datasheet-driven, note the datasheet document/section it needs (`find docs/ -name "*.pdf"` to confirm the document exists).

7. **Force genuine breadth.** Don't let all candidates be the next link in the most recent chain. Run `.index/schema.yml`'s `concept_frequency` query (`grep -h '^- ' .index/sessions/*/concepts.yml | sed 's/^- //' | sort | uniq -c | sort -rn`) to see which peripheral domains are saturated versus barely touched — cite the actual counts (e.g. "gpio: 5 sessions, dma: 0") when justifying a candidate. Explicitly consider the full trajectory named in CLAUDE.md's Scope (boot sequence, GPIO, interrupts/NVIC, timers, UART/I2C/SPI, DMA, ADC, PWM) and cross-platform angles, include at least one cross-platform candidate if the done set supports it. This frequency count is a descriptive signal only — it does not replace the hand-curated judgment in `.index/selection-context/`, which stays a human/agent judgment call, not a formula.

8. **Report back** a plain list of the candidates (title, target, classification, rationale, prerequisite chain), plus — if any datasheet pages were rendered — the full list of `.tmp/*.png` files produced this run mapped to their section/page, plus — if step 1 found anything — the sibling-repo awareness section (which repos exist, whether each was refreshed or skipped and why, and the handful of recent session facts pulled from each). Not a user-facing menu, no questions asked — structured findings for the calling conversation to present interactively.
